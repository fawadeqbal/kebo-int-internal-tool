# Single source of truth · PR 4 of 5: plans follow the dates

Audit §1 #9, §3.7, §4, §5, §7, §8 "PR 4"; owner decision §10: ONE READY DATE PER FACTORY. Builds on PR 1–3.

1. Ready date per factory: a per-factory ready date on the order (e.g. on the factory order / per factory
   of the order lines — choose the model that fits the existing factory order + FactoryPaymentPlan
   structure). The order's ready date = the latest of its factories' (derived, not stored separately).
   Each factory's PO, factory payment plan "on ready" rows and production checklist use that factory's
   date. Backfill: every factory of an order gets today's Order.readyOn.
2. Customer payment plan due rules like the factory plan: PaymentPlanItem gets dueRule (on_ready,
   on_ship_plus_days, after_papers, fixed) worked out live from the derived dates (ready = latest factory,
   ship = primary shipment departedOn); a date typed by hand becomes `fixed`. Remove datePlan's one-time
   dating. Backfill rules from balanceTerms; rows with hand dates → fixed.
3. Rebuilding the plan from the route keeps hand-edited instalments (only rows still equal to their
   generated values are rebuilt). Plan labels built from amounts ("Deposit 30%" computed), not stored text.
4. The order starts with the payment route implied by the accepted terms (letter_of_credit → LC route,
   against_bl_copy / before_shipment → informal with that balance timing), shown "from the quotation" and
   changeable. Optional backfill for orders with balanceTerms=letter_of_credit and no route.
5. Factory offer gets a structured advance % (`FactoryQuote.advancePercent`, default from Settings), used
   to seed the factory payment plan and printed on the PO; the free-text payment terms stay as a note.
6. Payment.kind worked out from what the money settles (deposit / balance); stored only for "other".
Tests for each.
