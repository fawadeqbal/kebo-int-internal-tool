# Company backup and restore — plan (paused 29 Oct 2026, to continue)

Work in progress on branch `feat/company-backup`: only `apps/api/src/platform/backup-crypto.ts` (untested draft of the encryption) exists so far. Everything below is still to build.


The owner decided:
- Who: each company's Super Admin can DOWNLOAD its own company's backup (Settings → a new "Backup" section, visible only to Super Admin). The platform admin can download any company's backup AND is the ONLY one who can RESTORE (platform panel, company page). Log every backup and restore (platform log via CompaniesService.log, and the company's audit/history where natural).
- Restore mode: REPLACE the company's current data with the backup. Before replacing, ALWAYS take a safety copy of the current state (reuse/extend CompanyDataService.archive() in apps/api/src/platform/company-data.ts) and report its key. A backup of company X restores only into company X (same company id); refuse another company's backup clearly.
- Secrets included, file encrypted: the backup includes everything needed to work as before, including users' password hashes and two-step secrets (unlike the current platform export, which strips them). The WHOLE file is encrypted with a password chosen when downloading (min 12 chars; asked again on restore). Wrong password or a tampered/truncated file is refused clearly before anything changes.

Existing code: company-data.ts has tables() (company tables in safe delete order), fileKeys(), clear(), export() (zip of data/<table>.json + files/), archive() (zip into storage archives/…). Platform controller apps/api/src/platform/platform.controller.ts (companies/:id/export). Web platform panel apps/web/src/app/platform/…; company Settings page apps/web/src/app/(app)/settings/page.tsx (tabs incl. "website-form", "address": follow that pattern for "backup"). Isolation: owner connection prisma.platform with explicit company_id; RLS policies use app_company(); same-company triggers on FKs; caches keyed by company (prisma.forget(companyId), ReadCache).

Requirements
1. Format (.kebo-backup): one encrypted stream of a zip containing manifest.json (format version, created at, app version if available, last applied Prisma migration name, company id/slug/name, per-table row counts, file count + bytes, sha256 per data entry), data/<table>.json (ALL columns, exact: Decimal as strings, timestamps ISO with zone, bigint as string, bytea base64), files/<storage key>. Encryption: node:crypto only; scrypt (or PBKDF2-SHA256, high iterations) with random salt in a small plaintext header; AES-256-GCM in fixed-size chunks, nonce from a counter, chunk index + final flag in AAD (detects reorder/truncation). Unit tests: round trip, wrong password, flipped byte, truncated, swapped chunks.
2. Download streams (never whole file in memory). Super Admin: POST from Settings → Backup with the password in the body. Platform admin: from the company page. Short plain UI note: what's inside, keep the password safe, without it the backup can't be read.
3. Restore (platform admin only). The live proxy limits request bodies to 30 MB and can't be changed now → CHUNKED upload from the browser (e.g. 8 MB parts to an upload session, assembled to a temp file on the API, total cap RESTORE_MAX_GB default 5, abandoned sessions cleaned up). ALSO a CLI for big files on the server: `docker compose exec api node apps/api/dist/cli/company-backup.js restore <slug> <file>` and `… backup <slug> <out-file>` (password prompted or env), in the style of apps/api/src/cli/platform-admin.*.
   Steps: decrypt+verify WHOLE file and manifest first (no changes) → company id matches → schema compatibility (4) → end the company's sessions → safety archive → ONE transaction: delete company rows (children first; files NOT yet deleted) and insert backup rows (parents first), same-company triggers active → put backup files into storage → delete storage files of the old state not in the backup → forget caches. Failure before commit = nothing changed. Show a summary (rows per table, files, safety copy key). Must not touch other companies (test it).
4. Older backups: restore by column NAME. Backup columns that no longer exist → refuse naming them. Current columns missing in the backup → default (or NULL if nullable); NOT NULL without default missing → refuse naming it. Tables new since the backup → empty. Show the backup's last migration. Test a backup missing a nullable column.
5. Not restored: sessions and device push tokens (cleared — everyone signs in again). The companies row itself (name, slug, plan, status) is unchanged by a restore.
6. Tests (apps/api/test/company-backup.test.ts): full round trip with demo-like data and files (export → change/delete data and files → restore → every company table equal to before, files same bytes); wrong password; tampered; other company's backup refused; other companies untouched; Super Admin downloads own, manager/staff cannot, no cross-company download; only platform admin restores; chunked upload assembly; CLI parts where practical.
7. Docs: short section in docs/companies.md + pointer in docs/restore.md (UI, CLI, safety copy).
Keep UI wording short and plain like the rest of the app. Final report: what was built, files, test results, limits (size), production risks.
